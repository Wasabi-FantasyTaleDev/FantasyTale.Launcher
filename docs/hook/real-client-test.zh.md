# V3 实机测试步骤

[English](real-client-test.md)

先构建原生解决方案的 Release|x86。宿主与记录器分别是
`native/out/Release/nmcogame.dll` 和 `crash_recorder.dll`。
本流程属于 H8；原生测试通过不能代替实机验收，也不能据此弃用 V2。

## Modern 启动验收（2026-10-18）

本机客户端语料现已覆盖国服 2019（`cn-774`）、台服 2019（`tw-454`）及韩服的注册检查。这些只验证身份识别和添加流程，不能证明已进入游戏大厅。国服 2019 使用 cn-774 sub_A22290 解析的有序 SDO 参数及 cn-774 sub_A129B0 请求的版本 512 登录桥；其接口标识与已有桥接一致。台服 2019 导入 `NMCO_CallNMFunc2`，tw-454 sub_B926B0 使用共享认证封装，因此选择支持票据的 stand-in，而不是转发官方 messenger。

维护者在 ARM64 本机通过实际 Launcher 启动韩服 2026 原始加壳程序，停在声称缺少 `d3d9.dll` 的 Themida 弹窗。另一台 x64 电脑报告缺少 `NGClient.aes`，但目录内已有此文件。之前韩服使用修改后的脱壳程序，其成功记录不能作为原始加壳程序的验收。此装载问题仍待解决，不得将注册测试或脱壳程序启动当成原始客户端验收通过。

修正版 Launcher 已添加并启动两个 2019 版本的原始可执行程序。国服 2019 报告 Native 就绪及 `login bridge: launch ticket delivered`，随后在登录界面以 `0xC0000005` 异常退出，程序偏移 `0x0064EB8D`（cn-774 sub_A4EB50）。这只能证明认证桥已交付票据，不能证明服务端兑换成功或进入大厅。台服 2019 报告 `ticket provided`，完成共享 messenger 调用，并进入主菜单，显示原有角色 `[GM]Wasabi`。此结果验收台服启动与票据登录；实际对局及没有预装兼容文件的纯原始客户端仍需单独验证。

## 国服 2013 的启动器票据登录

对于 `cn-406`，先构建并运行 `tools/package-native.ps1`，再使用启动器的客户端定义
和服务器账号流程。该版本通过 `gamewidget-ticket` 与 `sdologinentry.dll` 选择桥接；
运行时部署会自动备份和恢复登录库、信使库。不要给此桥接使用下面的旧 schema 1 示例，
它要求启动器管理的 schema 2 会话及服务器签发的新票据。

服务器应公布 `cn-406`，并在该 profile 的本地覆盖中开启
`lobby.config.launcher_tickets`。API 与游戏监听器必须共用票据服务。
游戏原始版本号只是显示信息，不是启动器更新版本。接口依据和限制见
[原生契约](cn-login-bridge.md)。

2026-10-08 已验收：通过启动器真实后端的注册、账号登录、客户端登记和启动接口，
连接线上服务器启动国服 2013。原生宿主在 forward 模式报告就绪，交付带标记的票据，
客户端进入大厅且测试账号和角色正常显示。启动器停止接口执行成功，两份原 DLL 的
恢复后哈希与启动前一致，session.toml 已删除。本轮没有启用可选插件。
该结果覆盖原生票据登录和退出清理，不代表完整对局、所有插件、其他版本或全部前端交互已验收。

## 准备一个版本

使用一份测试客户端。把原有 `nmcogame.dll`、可能存在的 `nmcogame.nexon.dll`
以及 `session.toml` 另行备份并记录哈希。替换这些文件之前退出客户端。

* 所有已启用版本都使用 `standin`。国服 2011 与 2012 调用旧版接口，与新版相同，
  只是没有 flags 参数。
* 改回 `forward` 的版本（目前只有未启用的 `cn-735`）需要把原版 Nexon 库保留为
  `nmcogame.nexon.dll`。不要把另一个替身当作转发目标。

把新宿主放在游戏 EXE 旁边，继续使用该版本现有的启动参数和账号来源。
ID2014 的真实账号在游戏内登录框输入。第一轮只验证宿主，不添加插件，
先核对信使模式以及能否登录，再启用插件。

## 会话与插件

英文版提供完整的 ID2014 TOML 示例。按实际目录修改路径，从对应版本的
build TOML 读取时间戳。每个同时运行的测试实例使用独立日志目录。

把记录器的 `plugin.toml` 和 `crash_recorder.dll` 放在同一个插件目录，
在会话里填写该目录。记录器 id 是 `bubblefighter.fantasy.crash-recorder`，
版本 `1.1.1`，选项为 `enabled=true`、`max_records=32`、`max_kib=1024`、
`external_privileged=false`。宿主打开日志目录后，记录器在其中创建 `crash.log`。

后续单独测试字重时，复制其 manifest 并增加 id 为
`bubblefighter.fantasy.font-weight`、版本 `1.0.0` 的条目。
目前它只声明支持 kr-812、id-400、id-1809、cn-706、cn-717；
不要将它加入 cn-324 或 cn-279 的会话。

记录器每次启用都会清空原 `crash.log`，重启前应保留本次日志。
它观察严重异常，然后继续客户端原有的异常处理；记录可能对应后来被客户端处理的异常，
单条记录并不证明客户端崩溃。C++ 异常通知会被过滤；默认还过滤主模块之外的特权指令异常。
需要进一步定位时可以开启 `external_privileged` 再试。

输出有文件大小和记录数量上限；每份不可变模块快照最多 128 项，最多刷新四次，
每次扫描至多 4096 字节栈空间、记录 12 个候选地址。候选地址不等于符号化调用栈。
超过上限、并发或重入异常、fail-fast 终止、部分栈溢出可能无法取得完整记录。
文本日志不主动记录账号凭据，但转储内存和收到的封包字节可能包含私人数据。

诊断模式 1.1.1 已声明支持 cn-406，仍为可选插件，没有任何客户端版本默认选中它。
原生实现使用异常处理及经过校验的导入表写入，不依赖客户端固定地址。
`write_dump=true` 时尝试在首次严重异常后生成有大小上限的 `exception.dmp`；
`max_dump_mib` 默认为 32，最多 64。`receive_packets=true` 时在 `receive.ftnet`
记录主程序导入的同步 `recv`／`recvfrom`；`max_packet_mib` 默认为 16，最多 64。
动态／异步接收路径及发送流量不在覆盖范围。没有受支持的导入时，运行时日志明确报告
接收记录不可用，此时不会生成封包记录文件。

## 离线前置证据

2026-10-10，使用 `tools/verify-plugin/verify_plugin.py`，以构建标识 `kr-812`
对跟踪中的 KR2015 `BubbleFighterU.exe` 检查了
`native/samples/bubblefighter.fantasy.mid-match-exit` 0.1.2。五个 RVA 补丁全部命中
期望字节，工具报告的原始与改写分支目标也符合补丁定义。这只是前置静态检查，不能证明
真实对局中的对话框、relay 回复或场景状态切换已经工作。

验证工具现在也会把数字血量插件中已支持版本的描述表与 EXE 对照：PE 身份、准确的渲染调用
及原始目标、调用方七个参数槽的清理、资源函数签名，以及声明的最大血量虚表指针。
任一不符都会失败。字节全部吻合时，原生激活与运行时 locator 仍为待验收，退出码为 2，
不会冒充成离线完全通过。

```powershell
python tools/verify-plugin/verify_plugin.py native/samples/bubblefighter.fantasy.numeric-health --image 'kr-812=D:/test-clients/KR2015/BubbleFighterU.exe'
```

10 月 23 日对本机真实 KR2015 解包 EXE 的七项描述表前置检查全部通过。这不代表运行中的
玩家对象来源、血量显示、重生和插件组合已通过。描述表格式正确不等于 EXE 字节正确；
研究版本继续使用单独的 `--research-descriptors` 显式检查，不会因此启用未支持的版本。

管理端集成测试使用独立的合成 x86 客户端进程，分别以 id-400 和 cn-406 会话身份验证
就绪、接收字节、真实访问冲突、可解析的异常转储、日志保留与原 DLL 还原。这验证了通用
诊断链路，不能替代原版 cn-406 可执行文件接收路径及实际游玩稳定性的实机验收。

## 验收与恢复

1. 检查信使模式和构建标识是否正确。
2. 开启记录器后，检查插件结果为 `installed` 且出现 armed 日志；插件失败不能算通过。
3. 先测试登录和菜单，再测试普通房间与开始、加载路径。私下记录账号、版本、模式、地图和时间。
4. 如果退出，保留 `fthook.log`、`crash.log` 以及同一场景的服务端 packet 记录，
   用该版本 corpus 对照异常地址与包顺序。
5. 单独确认字重的可见效果，不能把特征码命中当作视觉验收。
6. 测试后恢复原宿主与会话，或继续保留独立测试副本；不要分发含账号或票据的会话文件。

把实际版本、插件组合、结果行和游戏内现象填写到 roadmap 的 H8 表。
未实测的版本继续标记为待验收。
