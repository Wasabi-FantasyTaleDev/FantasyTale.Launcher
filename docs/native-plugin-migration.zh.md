# 原生插件仓库迁移

本文记录源码依赖审查和将泡泡战士原生集成迁入私有游戏仓库的验收条件。
Auto Dash 和诊断模式在游戏仓库中已有独立公开 ABI 构建；认证和宿主拆分仍未完成。
这些独立原生检查不代表游戏行为已经验收。

## 当前依赖清单

| 组件 | 当前源码依赖 | 边界问题 |
| --- | --- | --- |
| Auto Dash | `plugin_abi.h`、`pattern.h`、`session.h`、TOML 解析器；链接 `fthook.vcxproj` | 使用运行时的 C++ 模式解析和字符串转换；工程还导入启动器仓库的原生构建文件。 |
| 诊断模式 | `plugin_abi.h` 和 Windows 系统 API | 原工程虽未依赖 runtime 实现，仍导入 Launcher 共享构建文件；独立工程现只使用固定版本公开 SDK。 |
| 韩服认证 | `plugin_abi.h`、`pattern.h`、`session.h`、TOML 解析器；链接 `fthook.vcxproj` | 目前仍自行读取 `session.toml`。运行时 3.4.0 已提供单独授权的认证回调；插件改造和独立构建验收仍未完成。 |
| `nmcogame` 宿主 | runtime 的引擎、会话、日志、状态、控制和插件运行 API；链接 `fthook.vcxproj` | 它拥有游戏专用转发和登录行为，但直接调用 runtime 内部服务。 |
| 原生 SDK 导出 | `plugin_abi.h`、样例、许可证和说明 | 这是有用的 C ABI 边界，但目前没有向上述 C++ 集成提供所需服务。 |

插件 ABI 已提供有界日志、经过校验的选项、镜像扫描和读取、定位器注册、
暂存写入、Overlay 和 companion 回调。应保留该 C ABI 及其不得跨模块转移
CRT 所有权的约束。不要通过复制内部 C++ 头文件或 runtime 静态库，把内部实现
直接当成公开 SDK。

## 目标依赖边界

1. 游戏仓库固定使用有版本的 SDK 导出。原生工程只导入该导出和 Windows 构建工具，
   不通过相对路径访问启动器检出目录，也不链接启动器 runtime 工程。
2. 模式解析和通用文件/配置辅助函数应由有版本的 SDK 函数提供，或使用有意固定版本、
   许可证独立的依赖。每种选择都要明确版本、所有权边界和许可证声明。
3. 为韩服认证插件实际需要的认证数据使用范围窄、可检查结构大小版本的宿主回调。
   默认拒绝访问，只向明确授权的插件身份开放。回调只把当前启动所选的票据、地址和
   关联 ID 写入调用方提供的有界缓冲区；会话缺失或不匹配时返回明确错误，绝不记录票据。
   不要暴露完整会话对象，也不要让游戏模块解析启动器私有的会话文件。
   运行时 3.4.0 通过 `fthook_get_authentication` 提供仅入口函数期间可调用的
   `copy_credentials` 接口。托管模块在 `LaunchPlan.AuthenticationPlugin` 中明确指定
   已选中的原生插件身份；不指定就不开放接口。授权检查会在部署前拒绝旧运行时包。
   运行时核对启动、游戏和版本标识，报告调用方所需缓冲区容量且不部分复制，
   并在入口函数返回后撤销读取权限、清除临时票据副本。
4. 为 `nmcogame` 定义由 runtime 提供的宿主契约，通过明确的 C ABI 传递会话校验、
   插件激活、就绪/状态报告、控制请求和凭据交接。游戏专用消息转发及登录行为留在
   泡泡战士仓库；通用会话、插件生命周期和控制实现留在 runtime。
5. 迁移过程中保留插件 ID、选项名与默认值、客户端兼容范围、profile 的必装和推荐规则，
   以及已发布包的不可变字节。只有在对应 profile 和发行元数据同步更新时，才调整 runtime
   最低版本。

## 迁移顺序与验收

1. 发布并固定 SDK 导出版本，包含 ABI 版本、runtime 兼容范围、头文件、样例、许可证声明
   和机器可读哈希清单。
2. 先迁移 Auto Dash，因为它不需要认证信息。改用导出的 C ABI，从干净的游戏仓库检出
   构建，并运行原生契约测试。
3. 迁移韩服认证前，先加入并测试有界认证回调。验证会话缺失、不匹配和有效三种情况，
   确认票据不会进入日志或构建产物。
4. 只有 runtime 宿主契约能在隔离测试中复现 `nmcogame` 当前的就绪、失败、控制和登录行为后，
   才迁移该组件。
5. 每个目标仓库都要使用固定输入从干净检出构建，并验证插件加载、profile 必装行为、
   已保存选项与真实启动器的配合。
6. 分别迁移源码所有权和包发布。不要为了匹配新仓库布局而重建或替换不可变的商店发行包。

Auto Dash 在游戏仓库中已有独立实现和测试。诊断模式已从游戏仓库的集成快照迁至
`native/crash-recorder`，生产源码字节保持不变。游戏提交 `2af17a5` 的干净源码导出
通过固定版本 SDK 校验，并独立构建 DLL 和两个测试程序，没有使用 Launcher 构建文件
或 runtime 静态库。加载器只使用公开 ABI，覆盖九个独立进程场景：异常记录、关闭状态、
无效选项、文件失败、容量限制、已处理／致命异常的 minidump，以及真实同步回环网络接收。
清理会等待观察器退出，卸载前恢复合成宿主中的导入表。致命异常子进程必须按访问违规
退出，并保留可解析的转储。
