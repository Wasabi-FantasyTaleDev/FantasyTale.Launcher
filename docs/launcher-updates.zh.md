# 启动器自身更新

[English](launcher-updates.md)

弃用版本过渡期已结束。正式更新索引直接通过 `deprecated_max_version` 声明包含该版本在内的弃用边界；打包不再生成独立策略文件，更新检查和离线恢复均读取已验证的索引。未知的新增字段继续按可选信息处理，产品、平台、路径和文件完整性仍严格校验。

## 原生更新与回滚验收

2026-10-24 的验证使用当前 0.1.25 Windows ARM64 原生宿主、随构建复制的外部更新程序，
以及两份独立安装目录。两个本地 HTTP 测试源都要求临时测试密钥生成的分离签名；
生成测试发行后已丢弃私钥。产品来源仍由运营者自行选择是否配置签名。

正常候选只修改一个样式文件。校验下载完成后让来源返回 HTTP 503，点击重启仍完成了
该对象替换，重新打开原生主页，并在新进程确认前端就绪后提交。索引内全部 234 个文件
均与所选清单相符。

故障候选仅将 HTML 入口改为不包含就绪桥接代码的合法空白页，实际观察到了原生空白窗口。
现有的 90 秒启动期限届满后，更新程序停止候选进程，恢复原 HTML 并重新打开正常主页。
全部 234 个恢复文件均与独立重建的基线一致，失败清单仍被禁止自动重试。

两个场景都只请求了一个变化对象，来源配置及独立本地文件保持不变，均未残留事务日志或
原文件备份。本地证据位于 `artifacts/native-update-20261024/receipt.json`，同目录保留
签名清单、HTTP 请求审计和进程生命周期记录。本次验收覆盖本地原生更新与回滚流程，
不代表生产密钥管理、公开签名源、x64 便携包或实际游戏流程已完成验收。

## 可立即操作的完成状态

更新显示“已就绪”后，“重启并更新”可以立即使用已验证的暂存目录；任务显示“失败”后，
也可以立即重试。下载、文件验证和恢复状态写入全部完成后，任务状态和更新状态会一起
发布，后台 Task 的完成记账不会再短暂拒绝界面已经允许的操作。取消时会等传输停止后
才允许清除任务记录，退出程序仍等待自己持有的后台任务结束，再释放网络资源。

## 整包回退失败后的重试

增量暂存与完整压缩包回退都失败后，点击“重试”会恢复所选更新原先需要修改的文件列表。
压缩包分卷的进度列表不会被当作下一次更新的文件计划。整包下载暂停后继续也遵循同一逻辑：
先尝试增量文件，增量传输再次失败时才回退完整压缩包。已校验的暂存对象会保留复用，
本地未变化的文件不会进入增量任务列表。失败的任务不能因跳过实际文件而错误变成已就绪。

独立 Windows x64 桌面验收让增量对象和完整压缩包都先返回 HTTP 503，再仅恢复压缩包。
实际点击“重试”后，程序先重新尝试原来的变化对象，再下载完整包。点击“重启并更新”后，
外部更新程序安装所选发行内容，重新打开主页并完成前端健康确认。安装后的全部 990 个文件
大小和 SHA-256 均与所选清单一致，本地来源配置保持不变，没有残留安装日志或失败发行标记。
重启后的前端在 3,496 毫秒确认就绪。本次为未配置签名的本机 HTTP 测试，没有发布生产更新，
不能替代公开来源的自动更新验收。

## 易读的更新清单

更新清单以人类易读性为先：文件条目之间保留空行，等号两侧保留空格。发布流程不以旧版
读取器兼容性为目标，也不沿用旧版 256 KiB 清单限制。主索引和别名索引写入相同的 UTF-8
字节，记录的 SHA-256 对应这些实际字节，不受系统换行转换影响。

## 前端独立发布

在 `web` 中运行 `npm run type-check` 和 `npm run build`，然后执行：

```powershell
python tools/publish-launcher/publish_frontend.py --baseline artifacts/accepted/public --frontend web/dist --output artifacts/frontend-release/public --backend-version 0.1.19 --revision 1792488000
```

基线必须是已验收的后端发行目录。工具校验基线中的全部文件，保留后端文件身份，
将整个 `wwwroot` 替换为新构建结果，不重新编译 .NET。显式指定的后端版本必须与基线
一致；需要新增桥接接口的界面必须先发布对应后端。生成的完整索引也能为旧安装补齐该后端。
本地哈希相同的文件直接复用，因此只下载变化的前端资源。重启后统一切换；旧哈希资源
随事务清理，失败回滚时恢复。

部署分为可独立重试的两个阶段：

```powershell
python tools/publish-store/upload_alist.py --input artifacts/frontend-release/public --base-url https://files.example.org/ --catalog FantasyTale/launcher/win-x64/current.toml --phase incremental
python tools/publish-store/upload_alist.py --input artifacts/full-release/public --base-url https://files.example.org/ --catalog FantasyTale/launcher/win-x64/current.toml --phase archive
```

完整发行时两个阶段使用同一目录。增量阶段先验证不可变对象，再发布更新索引；
整包阶段要求完全相同的索引已上线，不重复传输这些对象。前端独立发布不生成完整压缩包，
如需更新首次安装包，应另外生成与新索引对应的完整发行目录。默认 `all` 先发布索引，
再上传可选的完整包。

启动器更新复用现有 HTTP／AList 来源适配器和下载引擎。发布工具扫描完整的构建目录，
自动生成文件索引，不需要手工维护文件清单或密钥。游戏原始版本号与启动器发布标签无关，
启动器发布标签本身也可以不填写。

关于页面读取正在运行的宿主程序集版本，而不是更新索引的显示标签。
`Directory.Build.props` 为普通构建和发布包提供唯一的版本值，需要修改版本时先修改此处。
构建及打包命令会拒绝不一致的版本覆盖，打包时还会核对实际托管组件版本，再生成更新源。
下载页出现新版标签，并不代表新版可执行文件已经安装或正在运行。

检查失败与更新失败分别提示。无法连接或校验更新源时，只提示暂时无法检查更新；只有已验证存在新版且下载或启动失败时，才提供手动更新页面。不能确认最新版本不会触发此弹窗。

“设置 > 更新 > 查看详情”还会显示选中来源及精确发行索引对应的上次外部安装失败结果。
如果更新程序有记录，会展示安装阶段和十六进制 HRESULT；旧版更新程序可能仅提供结果。
这些缓存诊断不包含异常原文或下载地址，可在现有弹窗内复制。本地存储失败后，即使暂存
文件已恢复到可以重试的状态，仍可查看上次诊断。安装成功、选中其他发行内容或编辑来源
后，此诊断视图会清除。

## 当前索引格式与发布检查

`schema = 1` 表示索引格式版本，`version` 仅表示发布标签，`revision` 用于推进发布选择。
正式版与预览版使用同一格式及默认的架构更新入口。`-SourcePrefix` 只改变不可变文件对象
的存放位置，不改变检查更新的入口；更换入口必须显式填写 `-FeedPath`。已经安装的
启动器会保留自己的更新源配置。

本产品尚未发布。当前格式以人类易读的 TOML 和完整文件清单为准，旧测试版读取器不再作为
兼容目标或发布门槛。文件表之间保留空行，赋值符号两侧保留空格；索引字节数和文件数量
不设固定的应用上限。

先发布索引引用的全部文件对象，再替换更新入口。发布时一起验证当前发布工具和读取器：
索引原始字节与哈希、变更文件选择、暂存校验、断网任务恢复、外部更新程序安装，以及前端
启动健康确认。传输失败后的重试和回滚分别验收。只有暂存成功的收据不能代表安装成功。
已经废止的旧读取器流程保存在私有废弃记录中，不再作为开源或发布准备的要求。

## 来源与发布

正式版本仅面向 Windows x64 发布。ARM64 构建通过 `-Platform win-arm64` 保留供维护者测试，
不作为另一个正式发布目标。发行打包入口会构建独立运行的启动器、验证外部更新程序和完整
文件内容，并一起生成文件索引和更新源配置：

```powershell
pwsh -File tools/package-launcher.ps1 -Output artifacts/launcher-release-next
```

发行包包含与启动器架构相同、可独立运行的 Overlay 程序，以及其 WindowsDesktop 运行时、
WebView2 加载器和界面文件。这两个程序均无需用户安装开发用 .NET 运行时；WebView2 Runtime
仍是外部运行条件。打包同时检查对应架构的压缩包解码器及许可证；缺少 Overlay、架构混用、
夹带本机 Overlay 浏览器配置等情况会阻止打包通过。验证器只执行外部更新程序的无参数入口，
不会打开 Overlay，也不代表已经完成游戏实机显示验收。

默认使用官方 AList 根地址 `http://archive-cn.600819.xyz:5244/`，读取
`FantasyTale/launcher/<platform>/current.toml`。`package/` 目录自带
`launcher-update.toml`，其最低内部编号与本次生成的索引编号一致，避免初次安装时
把服务器上的旧构建识别为更新。`public/` 包含可上传的索引和不可变文件对象，
不包含更新源配置。上传仍是独立步骤，打包成功不代表远端索引已经可用。请使用新的输出目录。
构建前先在 `Directory.Build.props` 中修改发行版本。本地构建、关于页、API 请求和
发行包均使用这一处版本值。构建时不允许通过命令行覆盖版本；打包的可选 `-Version`
仅用于核对是否与仓库一致。生成索引前还会检查实际发行组件的产品版本，拒绝旧构建或混合版本。
主程序将 Overlay 作为构建依赖自动还原，并通过 MSBuild 获取辅助组件的实际输出目录，
同样支持 `--artifacts-path` 指定的独立目录。运行 `python tools/test_host_helpers.py`
可核对全新目录还原、组件版本及复制后的辅助程序和资源哈希，无需打开 Launcher。
其他部署可以覆盖 `-BaseUrl`、`-Kind http`、`-SourcePrefix`、`-FeedPath`、`-Platform`
或 `-Revision`。此脚本不会打开启动器或游戏窗口；不同架构的发行包
需要在匹配的 Windows 架构上执行外部更新程序验证。`-FeedAliases` 声明保留的更新入口；
默认固定入口会保留曾经随预览包分发的入口。打包工具生成内容相同的索引和独立的发布
元数据，AList 上传工具在文件图验证完成后更新这些别名。此元数据不属于客户端索引，
不会改变索引格式。

打包时还会在对应架构的 `portable/` 目录生成便携 ZIP，内容来自同一份经过验证的文件
索引及发行包更新源配置。上传工具先验证手动下载包，再替换更新入口。
其他发行方可以通过 `-ManualDownloadUrl` 指定下载页面。`launcher-download.toml`
独立声明自己的 `schema = 1` 与 HTTP(S) `url`，不依赖自动更新索引。自动更新失败时
会出现可取消的 WinUI 风格弹窗，只有用户点击后才打开浏览器。已经检测到版本时显示
该版本；检查失败、无法确认最新版本时会明确说明，不能编造版本号。关闭同一次失败的
提示后，不会在每次状态轮询时重复弹出。

在启动器可执行文件旁放置 `launcher-update.toml`：

```toml
kind = "alist"
base_url = "https://files.example.org/"
```

普通 HTTP 静态托管使用 `kind = "http"`。默认读取
`launcher/<platform>/current.toml`，其中平台按启动器进程架构自动选择
`win-arm64`、`win-x64` 或 `win-x86`。可选的 `feed_path` 可以覆盖这个位置。
AList 的地址是 API 根地址，文件位置相对于 AList 虚拟根目录。
可选的 `minimum_revision` 记录初次分发版本的内部基线，默认值为零。
启动器不会从第三方游戏或插件商店猜测自身更新来源。

发布配置 TOML 只需填写两个目录，相对路径以配置文件所在目录为基准：

```toml
input = "build"
output = "public"
```

在仓库目录执行：

```powershell
dotnet run --project tools/publish-launcher -c Release -- path/to/publish.toml
```

输入必须是完整构建，包含启动器可执行文件、`wwwroot/index.html`、`updater/` 下的
更新程序及全部运行依赖。请使用目标运行架构发布；交叉发布时在配置中填写 `platform`，
否则默认使用发布工具自身的进程架构。`version` 是可选显示标签。内部发布序号自动使用
发布时间戳；已有单调构建编号的 CI 系统也可以填写 `revision`。

输出包含按 SHA-256 保存的不可变文件对象，以及原子替换的当前文件索引。同一份输出可以
挂载或同步到 AList，也可以直接通过 HTTP 提供。上传时先上传文件对象，再替换当前索引。
`source_prefix` 和 `feed_path` 可调整虚拟目录位置；已存在的文件对象会复用。
发布工具排除更新来源配置、调试符号和安装日志，发现本地秘密文件或覆盖配置会报错。

要签名生成的清单，可在发布 TOML 中加入 `signature_path`、
`signature_private_key_env` 和 `signature_public_key_path`。环境变量中放置
base64 编码的 PKCS#8 RSA 私钥。发布工具只写出 detached 签名和公钥
SubjectPublicKeyInfo，不会写入或记录私钥。将生成的公钥复制到安装目录的
`launcher-update.toml`，设置为 `signature_public_key` 后，再向用户启用签名路径。

明确选择签名发布时，发布器还会生成本地上传记录 `.fantasytale-signature.json`，
用 SHA-256 绑定当前索引、独立签名和公钥文件的实际内容。AList 上传器在认证前检查
这些文件，先上传签名相关文件并通过匿名下载验证，再替换索引；遇到远程并发修改或
本地文件变化时拒绝继续发布。此记录需保留在生成目录中，本身不会作为发行文件上传。
各元数据路径及其临时文件必须互不重叠，也不能覆盖不可变内容对象。
已经用于签名发布的输出目录不能改为未签名发布。

这仍然是可选的发布能力，普通来源无需配置密钥。上传的公钥文件不会自动成为客户端
信任的公钥；客户端只使用本地已经配置的公钥校验签名。

当前索引是普通 TOML，包含产品、平台、内部发布序号、可选标签，以及自动生成的目标路径、
来源路径、大小和 SHA-256。需要签名的部署可以在清单旁放置 detached RSA-SHA256 签名，
并在 `launcher-update.toml` 中同时配置：

```toml
signature_path = "launcher/win-x64/current.toml.sig"
signature_public_key = "base64 SubjectPublicKeyInfo"
```

签名覆盖清单的原始字节。两个配置必须同时存在；公钥错误、签名缺失或清单被修改都会作为
完整性失败。验证通过的独立签名会与所选清单一起保留。开始下载、离线恢复已保存的下载任务，
以及外部更新程序安装时，都会使用当前配置的公钥重新验证这份清单和签名。
因此，启用签名或轮换公钥后必须重新取得可验证的更新信息，不能直接信任之前下载的未签名清单。
旧版保存的签名更新如果缺少本地签名文件，需要重新检查更新。未配置签名的来源仍按原方式工作。
现有未签名部署仍然兼容，直到发布方提供公钥和签名文件。校验值仍用于检查
下载文件是否完整或发生变化；提供哪个发布版本由所配置的来源决定。

生成的启动器索引也可以使用商店共用的 AList 上传工具：

```powershell
# 在当前环境中设置 FT_ALIST_USERNAME 和 FT_ALIST_PASSWORD。
python tools/publish-store/upload_alist.py --input ./public --base-url https://files.example.org/ --catalog launcher/win-x64/current.toml
```

`--catalog` 使用实际的 `feed_path`。上传器识别启动器文件行，在替换可变索引前验证内容，
临时网络错误时重新取得下载元数据再重试。管理员认证不会发给文件直链主机。
候选索引可与生产索引分开，直到外部桌面更新及健康确认验收通过。

发布桌面项目时，更新程序现在按相同的运行时架构和独立运行设置单独发布。
独立发行包包含更新程序自己的 .NET 运行时，因为更新时它会被复制到应用目录之外，
不能依赖启动器目录或目标电脑上安装的 .NET。

可以在不打开启动器的情况下验证 Windows 独立发行包：

```powershell
dotnet publish src/FantasyTale.Launcher.Host -c Release -r win-x64 --self-contained true -o portable
python tools/verify-updater-package.py portable --platform win-x64
```

验证工具检查两个可执行文件的架构和更新程序的运行时依赖，在执行之前拒绝输入包任何位置的
本地状态、链接、浏览器配置、本地覆盖配置、日志、转储和调试符号。正常发布仅在本地构建
输出保留 PDB。此文件名检查不是内容或素材许可审查，另见[经审查的源码导出](source-export.zh.md)。
随后将更新程序复制到独立目录，禁用外部
运行时查找并运行更新程序的无参数入口。它不会替换应用文件。发布工具与更新清单读取端
均要求完整发行包包含启动器、前端及更新程序可执行文件。

对于依赖已安装 .NET 的发行包，传入 `--runtime-mode framework-dependent`，验证运行时
模式并使用正常安装的 .NET 运行外部副本。两种模式都会拒绝更新程序目录中的其他架构构建
或发布目录。普通构建复制时排除先前的 RID 输出，避免交叉发布后意外混入另一套独立发行包。

## 下载与重启

“设置 → 更新”分别提供启动器和客户端的更新选项。默认在启动时及每三十分钟检查，
自动下载默认开启。仅自动下载不会自动重启启动器。主页和下载页共享真实任务、总进度、
当前文件进度、速度、预计时间以及暂停／继续操作。手动暂停会在重启后保留；已完成暂存的
文件重新做本地校验，文件齐全时无需请求来源即可恢复到等待安装状态。

更新状态记录通过原子替换发布。读取器保留完整的上一份状态，同时允许更新工具发布下一份，
不会因状态读取阻止文件替换。保持读取器打开的回归测试覆盖了这个边界，
不代表其他外部文件锁或所有断电时序均已验收。

读取器遇到 Windows 共享或锁冲突时最多重试 200 毫秒，以容忍状态替换的短暂竞争。
持续占用和其他错误仍会失败；测试分别覆盖临时占用解除及持续占用被拒绝。

检测到已验证更新后，侧边栏底部显示圆形下载入口，悬停时提示有可用更新，点击可打开带
动画的 WinUI 确认弹窗。仅检测到可用版本时不会自动打开下载弹窗。首次弹窗
显示当前版本与可用版本，确认后下载更新。下载进度展示百分比、速度和预计时间，右上角 X、
“后台更新”按钮、Esc 或点击弹窗外部只隐藏窗口，下载仍继续。侧边栏显示实时下载进度圆弧，
下载完毕后切换为旋转圆环，用于校验及等待安装；点击可回到当前更新阶段。下载与校验完成后，
会主动弹出安装确认，即使此前关闭了下载进度窗口。弹窗说明更新已下载完成，询问是否现在应用，
并提示更新过程中可能导致游戏中断。提供“立即更新”和“稍后”；选择稍后会保留已下载文件，
本次启动内同一份更新不会反复提醒，仍可从侧边栏重新打开。只有确认安装才启动外部更新程序并重启。安装进度
不能关闭，没有关闭按钮，Esc 与点击外部也不会关闭。设置、下载页重启入口使用同一流程。
手动检查发现更新后也会打开对应弹窗，即使此前已经取消过提示。

每次界面正常启动后都会检查更新，原来关闭了定期检查的安装也不例外。定期检查选项只控制
运行期间每 30 分钟追加检查。自动下载仍为可选，不能代替安装确认。安装许可绑定到当前
清单与已就绪任务，更新变化、取消下载或失败会使此前操作失效。交接失败后恢复关闭能力，
重试需要用户再次操作，不会自动循环重试。

已经下载完成但没有安装就关闭启动器时，会保存当前清单与已校验文件。下次启动只做本机
校验后直接询问是否安装，不重复联网下载；即使更新源暂时无法连接，也能恢复待安装状态。

确认自动重启后，先校验选定更新和暂存文件确实就绪，再结束启动器管理的游戏及本机
服务端。没有显式结束许可的旧重启操作仍拒绝在游戏运行时执行。开始交接后，宿主阻止
启动新的游戏；交接准备失败会恢复正常启动能力。已安装的更新程序先复制到应用目录外，核对父进程身份和暂存文件，
通过限制当前用户并校验对端 PID 的命名管道确认就绪，然后等待原启动器退出再替换文件。
它不会强行结束原启动器。

安装会用持久化日志保留原文件，直到新进程确认前端进入动画已经完成。更新程序提交安装前，
新启动器不能启动游戏。新版不能启动或未能按时就绪时，只结束本次启动的新进程，恢复原文件、
移除新增文件，然后重开旧启动器。发现外部修改时保留恢复材料，不覆盖已变化的文件。

新版启动或完整性检查失败后，更新程序先记录来源身份和失败索引的精确哈希，再重新打开恢复后的启动器。
该更新会显示为启动失败，不会再次显示为等待重启。在保留此失败版本记录期间，自动下载、
重试以及清除任务都不能重新安装同一失败索引。可以使用“检查更新”寻找新发布；
其他来源或索引的结果不会阻止当前选择。

最近一次失败版本另存于 `rejected.json`，避免离线修复写入修复结果时将其
清除。没有此记录的旧安装仍可识别带来源身份的回退结果。

暂存或替换阶段的本地存储错误不会封禁该发行版本。成功恢复后，可以重新打开已校验的
暂存内容，但安装仍需要再次明确确认。重试前应释放所需磁盘空间或解除文件占用。
更新程序的 `outcome.json` 保留失败类别、阶段及数字 HRESULT，不保存异常消息或私有
请求地址。新读取器也能识别明确标记为存储错误的回退结果；没有类别的旧回退记录仍
保留原有的保守拦截行为。存储错误不会清除已有的启动或完整性失败版本记录。

主页没有当前文件进度时，总进度条占满可用宽度；出现当前文件时，带动画切换为两列。
“打开下载页面”位于次要操作之前，蓝色的检查更新、重试、继续或重启按钮保持在最右边，
按钮出现和位置变化均带过渡动画。手动检查只刷新入口和版本状态，用户从入口打开弹窗。

成功安装后还会记录属于该来源的文件路径、大小和哈希。后续更新只有在记录与已安装回执
一致、且旧文件内容未被修改时，才会移除新版中不存在的文件。移除的文件与被替换的文件
一起备份，新版启动失败时一并恢复。旧文件被修改会拒绝安装；健康检查期间被重新创建的
文件会阻止提交，并保留恢复材料。未记录归属的文件继续保留。旧格式安装的第一次更新
只建立文件记录，不猜测已有文件的归属，也不要求人工列出删除清单。

自动生成的前端目录 `wwwroot/assets` 按完整发行清单管理。更新会移除新清单中不存在的文件，
包括没有归属记录的旧安装所遗留的带哈希 JavaScript 和 CSS。扫描包含嵌套资源目录，进入目录前
拒绝链接，并限制扫描数量。新清单仍使用的文件会保留。移除的资源与更新文件一起备份，
新版启动健康确认失败时一并恢复。此生成目录之外未记录归属的文件，包括用户设置和客户端
数据，继续保留。

## 完整性与恢复

索引、文件列表、发行版本大小和持久化更新记录不再设定固定的应用上限，
来源文档读取接口也不再提供可选的字节上限参数。目标路径不能越界、
经过链接、使用 Windows 歧义名称，或替换更新来源配置。检查更新时会拒绝冲突或倒退的

当前安装支持新增、替换和移除已校验归属的文件。文件归属记录、替换和移除日志不再设定
固定字节或条目数量上限。文件与目录形态互换会在替换前报错，不擅自删除未知目录内容。
安装目录需要可写，不自动提权。
不能安全完成恢复时会保留日志和备份；保留的外部更新程序提供下述离线修复入口，修复时不要直接

## 中断更新恢复

更新策略支持包含多个 `[[sources]]` 的 schema 2。启动器按配置顺序检查来源，每个来源有三十秒
独立超时。第一个有效发行清单会结束检查，包括返回“当前版本”的情况；后续来源用于失败回退，
不会继续寻找更高修订号。来源失败或被拒绝时才检查下一个来源。取消检查会恢复之前的状态。
选中候选前会核对已安装和此前发现的发行元数据。每个来源分别保留已接受的修订号和索引
精确哈希，切换到备用来源、调整来源顺序或重启均不会清除。再次访问同一来源时，会拒绝
更低修订号，以及修订号相同但内容变化的索引。备用来源仍可提供自身有效的发行版本，
选中它不会覆盖主来源的历史；所有来源的历史与当前选择一起原子保存。
版本检查只读取发行索引及配置的签名，不打开本地程序文件。下载准备阶段才使用二至八个并发
任务比较本地文件，任务列表只显示变化文件，校验一致的内容从本地复用。
暂存阶段最多并发准备四个不同的内容对象。相同哈希的文件共享下载和续传对象，各目标文件
同步显示进度。缓存对象校验一次，下载保留引擎的 SHA-256 校验，本地复制后校验复制结果。

增量更新直接比较本地内容与目标发行清单，不要求先安装中间版本；格式兼容的旧版读取器可以
跨多个版本升级。对象传输及等价来源回退在有限次数重试后仍失败时，更新程序才尝试完整包。
可选的 `<feed_path>.archive.toml` 配套元数据绑定目标清单的精确哈希，声明 `format = "zip"`、
`"7z"` 或 `"rar"`，并用有序的 `[[files]]` 列出每卷的 `path`、`source_path`、`size`、
`sha256` 和 `volume`。不设置固定的压缩包大小或分卷数量上限。复用客户端解压器检查路径、
链接和分卷完整性，要求包含所有目标文件，并在暂存前按更新清单校验解压内容。
便携包中的来源配置不会替换本地更新来源；自动更新包不得要求交互输入密码。
默认发布 ZIP，其他格式使用相同的分卷元数据和解压流程。

部署时先发布通过校验的增量对象和更新索引，再单独上传完整包。完整包匿名校验通过后才
发布配套元数据，因此完整包上传慢不会拖延增量检查，也不会暴露尚未完成的回退包。
旧版读取器忽略配套元数据，继续使用原有增量下载流程。
暂存更新会保存选中来源的身份，外部
更新程序和重启恢复会继续使用同一来源。schema 1 仍然兼容。

来源顺序决定版本检查的优先级。通常将官方 Fantasy Tale Archive 放在第一位，官方 HTTP
镜像放在第二位；用户可以在不修改发布文件的情况下添加和调整顺序。

如果选中的启动器发行版来自与当前安装不同的已配置来源，独立更新程序只会在安装锁内重新读取并
精确匹配当前安装记录后授权这次归属转移。产品和包的身份仍必须一致，旧记录、归属文件列表及外部
文件哈希也会在替换前重新检查。只有健康启动确认成功时才提交新的来源身份；启动失败会恢复旧文件
和旧记录。普通客户端安装不适用这个例外，仍要求来源归属完全匹配。

换源进程回归覆盖 HTTP、AList 在旧来源已移除时启用或不启用可选签名的情况；独立的签名用例也保留
配置中返回 HTTP 503 的首选来源。暂存任务先在离线状态下恢复，再启动真实的独立更新程序。测试核对成功提交
及启动失败回滚后的旧文件、完整来源记录、本机设置和用户文件。这是使用测试启动器的进程验收，
不代替桌面渲染或公开来源验收。

启动器在创建正常窗口前检查未完成的安装日志。程序仍能启动时，会把日志和哈希交给应用目录外的更新程序，等待自身退出并确认日志未变化后离线恢复，再重新打开启动器。每个启动进程使用独立的临时请求文件，交接后清理，避免并发启动覆盖其他进程的请求。程序无法启动时，可运行保留的更新程序 `FantasyTale.Launcher.Updater.exe --repair <安装目录> <数据目录>`。它取得相同的锁，拒绝修复仍在运行的启动器，校验日志及事务文件哈希，然后离线恢复并写入结果文件。文件变化、备份缺失或更新程序冲突会保留恢复材料并报告 `recovery-required`，不需要网络或发布索引。安装目录的锁被占用时不修改文件和备份，释放锁后可以重试；损坏的日志也会保留供修复，不直接丢弃。

## GitHub 镜像选项

设置中的 GitHub 镜像加速使用已配置的镜像提供方。启用后，符合条件的 GitHub 请求（包括更新元数据和文件请求）可能经所选镜像转发。下载文件仍须匹配所选发行记录的大小与 SHA-256；但对于未签名的更新源，这些检查只能检测内容损坏，不能认证元数据及其发布者。配置的源、传输链路和转发提供方仍属于更新信任边界，不能将镜像转发视为端到端认证的更新传输。参见[网络设置](network-settings.zh.md)。

## 编辑更新源

升级后，保留在本机的内置旧 AList 更新源会自动使用当前内置源地址并开启优先 IP 访问。来源标识保持稳定，已暂存下载与已接受的版本记录继续有效。自定义路径、带签名的更新源和其他主机保留原有配置，策略文件本身不被替换。

在“设置 > 更新”中可以添加来源，编辑名称、传输类型、公开根地址和索引路径，并调整顺序。保存时会先验证整个列表再原子替换；配置无效或来源重复会保留原设置。请先完成或取消正在进行的启动器更新，再编辑来源。安装基线和已有签名配置会保留。文件来源不可用时，下载程序会检查其他已配置来源，仅使用修订号、版本、目标路径、大小和哈希均相同的发行内容。即使其他来源成功发现新版，各来源的失败原因仍可展开查看。官方 GitHub 索引部署和桌面验收尚未完成。
