# 插件管理

游戏运行中也可启用、关闭、切换版本或设置插件，修改会保存为下次启动的配置，并显示 InfoBar 提示。当前游戏会话及已部署文件保留启动时的快照。卸载会立即移除已保存的选择和插件库卡片，相关文件在客户端释放占用后再清理。卸载标记在重启后仍有效；重新安装相同且校验一致的版本时，可恢复保留的包而不修改运行中的文件。

统一插件通知支持 info、success、warning、error 四种等级。未安装或未启用的必需启动组件按插件卡片逐项展示。“启用后继续”会先安装缺失插件并启用组件，“仍要启动”仅确认本次启动，“取消”会停止启动流程。下载未完成或失败时不会继续启动。自动更新完成后，先刷新共享插件库，再显示包含新旧版本号的成功 InfoBar。主页和侧边栏的更新标记使用同一份插件库数据。插件方案会跟随已应用的新版本，并保留后续开关和设置修改。

商店安装可一次选择同一游戏的多个兼容客户端，包括不同客户端版本。任务只向共享插件库安装
一份校验后的包，并保存每个目标在排队时的插件选择，重启后也可恢复。如果下载期间改变了某个
目标的选择，完成时会跳过该目标的启用，不影响共享包和其他客户端。

“自动更新插件”默认开启，设置保存在 `client-updates.toml` 的 `auto_update_plugins`。
启用后台插件检查时，发现更新会排入共享插件库的升级任务，不受正在运行的客户端阻塞。
运行中的客户端保留当前选择，启用意图单独保存，退出后取得客户端锁再处理。
多个客户端共用同一发行版的下载任务，已经校验安装的包也可直接复用。关闭自动更新后，仍可检查和手动更新。
下载会绑定原插件选择，避免覆盖用户在下载期间做出的新选择。

插件页显示待应用数量及来源、内容校验或存储失败原因。文件替换插件会在下次游戏启动准备时
从新版插件包部署，不会因共享插件库更新而覆盖正在运行的游戏文件。

有可选插件尚在下载时开始游戏，会显示 Fluent 对话框并列出相关插件，可以等待完成后启动、
使用当前已安装的完整版本立即启动，或取消。切换客户端、服务器或账号会取消弹窗和待启动请求。
如果新增了其他下载任务，需要重新确认。必装插件、最低启动器版本和最新版要求仍由后端检查。
商店的多客户端勾选也允许包含正在运行的客户端，其新选择会在客户端锁释放后应用。

普通商店浏览复用短期共享清单缓存；点击商店刷新或检查插件更新时会获取最新信息。
同一来源的并发请求仍共用正在进行的获取任务。刷新失败会保留上次通过验证的快照并报告失败，
不会把缓存中的旧版本当作没有更新的证明。

[English](plugin-management.md)（以英文版为准）

设置中的“开发者模式”默认关闭并会保存状态，开启后显示“开发者选项”和“商店源管理”选项卡。
“上班摸鱼模式”（代码字段 `nsfw`）也默认关闭，开启后隐藏主页视频与图片。
开发者模式新增“资源 override 测试”，可选择客户端查看最近准备的资源修改、来源插件、
归档内成员的变更，以及当前物理 BFZ/PKN 是否为原版或补丁版本。此页只读检查文件，
不会应用补丁。开发者页中的商店源管理仍预留待实现。

商店安装对话框可以一次选择多个兼容客户端。下载任务只把经过校验的插件内容写入共享库，
并在旁车文件中保存客户端激活目标；插件安装完成后才会逐个重新验证并启用。

启动器也支持[文件替换插件](file-plugins.zh.md)，此类包不会由 FtHook 加载。导入包不能声明 `required_on` 或 `warn_on`。

打开“插件”页，点击“导入插件”，无需先安装或选择客户端。支持选择包含
`plugin.toml` 的文件夹，或将该文件放在根目录、或单层外包文件夹中的 ZIP。
弹窗校验包内容并显示插件名称、版本、文件数量和大小，确认后导入共享插件库。
兼容性决定哪些客户端可以启用该插件。新插件导入后不会自动选择；导入已有插件的
更高版本后，会为兼容且已选择该插件的客户端自动切换版本，保留开关状态和设置。

插件安装到当前用户的插件库，与启动器安装目录和游戏文件分开。新插件需要在对应
客户端中打开开关。游戏运行中的导入升级会等退出后再切换，待切换记录可以跨启动器
重启保留，应用前重新校验导入文件；用户之后改变选择会取消这次待切换操作。
每个客户端固定选择一个插件版本。
切换版本需要确认，默认保留兼容的共有设置，也可以在确认时明确选择新版本默认值。其他客户端保留各自的选择，旧版本也会
继续保留。游戏运行期间可修改下次启动的配置，当前游戏会话保留启动时的选择。

无法同时使用的插件可以通过 `plugin.exclusive_with` 声明互斥标识。主动启用其中
一个时，会关闭另一个可选插件，但保留它的版本和设置。必选组件不会被替换。
仅导入尚未选择的插件不会触发切换；同时启用互斥插件的无效配置会在启动前报错。

浏览插件库不需要先添加客户端。卡片按游戏和插件标识分组，同一张卡片内可选择不同发行版本。
更新提示仅属于当前客户端对应的游戏；启用操作精确匹配游戏、插件标识和版本，
不同游戏即使插件标识相同也不会误选对方的发行版本。

没有对应客户端时，也能先下载商店插件。点击“下载 / 安装”，选择“仅下载到插件库”。
下载使用统一任务队列，支持进度、暂停、重试和启动器重启后继续；完成后保存在共享插件库中，
不会自动启用。添加兼容客户端后，在它的插件页选择已下载的版本即可。如果无法使用某个发行版，
商店会说明是游戏未开放、不支持插件，还是缺少启动器支持的客户端版本。

插件格式见 [Hook 插件格式](hook/plugin-format.zh.md)。支持声明式补丁和原生 x86
DLL 插件。导入只读取数据与 PE 文件头，不加载或执行 DLL。游戏启动时运行时仍会
检查插件 ABI、导出函数、补丁位置和就绪状态；导入成功不代表已经通过真实游戏验证。

## 插件配置页

所有插件均可在 `plugin.toml` 声明设置项。启动器在保存客户端配置前校验类型、范围与
枚举值。可选的 `plugin-ui.toml` 能提供枚举值的本地化文字，也可指定独立 HTML 页面。
页面在隔离的 iframe 中显示，不能访问网络或启动器桥接接口，只能交换 schema 为 1
的选项消息；启动器会按插件声明校验返回的每个值。不提供此文件时使用统一设置表单。

插件可通过 `plugin-ui.toml` 的 `[[pages]]` 数组明确声明设置页。每页指定唯一的 `id`、
`kind`（`native` 原生表单或 `html` 页面）、包含 `en` 的本地化 `title`，并通过
`options` 列出 `plugin.toml` 已声明的配置项。HTML 页还需提供包内 `path`；
原生页由启动器为指定配置项生成控件，不提供路径。页序与声明一致，只有一页时不显示
页签。显式声明页面后，启动器不会额外添加统一设置表单。例如：

```toml
schema = 1

[[pages]]
id = "resolutions"
kind = "html"
path = "settings.html"
options = ["custom_resolutions"]
title = { en = "Custom resolutions", "zh-CN" = "自定义分辨率" }
```

此声明属于提供 `custom_resolutions` 配置项的插件，不是对所有 HTML 插件生效的规则。
`[[pages]]` 不能与 `[ui].page` 混用。文件缺失、页面类型错误、ID 重复或引用未声明的
配置项都会拒绝加载。HTML 页只能接收和修改该页声明的配置项，保存时仍按插件声明
校验完整草稿。

未启用的插件也能提前保存配置；设置属于所选客户端，不会修改安装包。取消会丢弃本次编辑。设置在下次启动游戏时生效，不是热更新。

需要可选的颜色预览时，可将[示例页面](examples/plugin-configuration/settings.html)
和[配套声明](examples/plugin-configuration/plugin-ui.toml)复制到声明了 `font_color`
枚举（`white`、`yellow`）的插件包。示例不会自动加入发布的插件。已有版本不可覆盖，
加入页面后需要发布新的插件版本。

HTML 必须是有效 UTF-8。使用内联 CSS、脚本和 data 图片；不能加载相对
路径资源、发起网络请求、提交表单、导航到启动器或直接调用桥接接口。先监听父页面消息，
再发送 `{ type: 'fantasytale:ready', schema: 1 }`。父页面会返回包含 `schema: 1`、
`language`、`options`、`values` 的 `fantasytale:configuration` 消息，并在选项或语言
变化后重新发送当前值。页面应检查 `event.source === parent`。发送 `fantasytale:change`、
`schema: 1` 和只包含已修改声明字段的 `values` 对象，更新编辑草稿；只有启动器的保存
按钮才会持久化。未知字段或无效值会导致整条消息被拒绝。不要把初始化消息回传为修改，
否则会产生消息循环。

页面可以发送 `fantasytale:resize`、`schema: 1` 和正安全整数 `height`，以 CSS 像素
报告内容的自然高度。应监听内容容器，而不是 iframe 视口，避免尺寸变化循环。
报告内容高度的页面会按内容调整尺寸，由外层弹窗统一滚动，避免展开时 iframe 临时出现
滚动条。未报告高度的页面保留原有视口与滚动方式。编辑区尺寸仍会平滑过渡。
顶部弹窗已有标题，自定义页面无需重复。

## 安装规则

导入时先复制到独立暂存目录，检查游戏、所选客户端版本、运行时要求、选项和补丁
定义。原生插件必须在声明的位置提供有效的非托管 x86 Windows DLL。正式安装前
重新比对预览时的完整文件列表与 SHA-256，再一次性将完整目录移入插件库。取消时
删除暂存文件，启动器重启时清理遗留暂存；已有插件目录不会被部分替换。

用户确认的本地导入可以安装明确列为商店管理的组件，但必须保留游戏定义或内置清单声明的
`update_source`。其他受保留的组件标识继续受到保护；同版本内置组件必须与完整原始快照一致，
新版本必须保留文件恢复策略。仅声明更新渠道不会让本地导入获得商店来源收据。同时不能声明
`required_on`，避免一次导入就为其他客户端增加强制要求。启动必需项及版本要求由游戏／客户端的 `client_policy_rules` 管理，
插件包不能声明启用策略；内置组件可以用 `update_source` 声明托管组件信息，更新不能改变这些信息或配置策略。任何已启用商店均可提供通过校验的同一组件发行版。组件 ZIP 同样经过正常预览、完整性检查和用户确认。

插件版本使用 SemVer，同一游戏、标识和版本不能重复导入或静默覆盖。修改内容后
应发布新的插件版本。这是插件包的规则，与游戏文件更新时可选的更新标签不同。
导入新插件版本也不会修改游戏的原始版本号。商店文件包现在通过共用下载队列安装到
同一插件库，详见 [商店来源](store-sources.zh.md)。
成功下载新版后，会把该客户端已启用的旧版切换为新版并保留兼容设置。

## 检查和应用更新

选择客户端，点击“检查更新”。启动器会从所有已启用商店查找已安装插件标识的兼容新版，
包括手动导入的插件和托管组件。原来源改名、换地址、停用或移除，都不会阻止其他已启用来源提供更新。
镜像提供相同清单摘要的发行版时可复用；最高版本对应不同内容时显示冲突，不会随意选取。

检查完成、更新等待应用及检查失败都使用可关闭的 InfoBar。关闭后，后台轮询不会重新弹出同一条提示；
主动重新检查可再次显示当前结果。内置标签为蓝色，有更新为绿色，必需为琥珀色，不适用为灰色。

检查会选择来源声明兼容当前客户端、且其最低启动器版本要求可由当前 Launcher 满足的最高新 SemVer 版本。
需要更高版本 Launcher 的新插件不会挡住可用的中间升级版本；没有可用升级时，保留当前已安装版本。
必须保持最新的组件仍要求使用该来源对当前客户端提供的最新版；如果需要升级 Launcher，会明确提示，
不会退回较旧组件。正式版只更新到正式版；
已安装预览版可更新到后续预览版或正式版。仅构建元数据改变不视为升级；同一版本序位
存在歧义时，会显示冲突。下载后仍要按插件本身的
定义检查客户端与运行时兼容性，目录声明不代表已经通过真实 Hook 验证。

“下载”会重新检查已启用来源、已安装版本、所选新版本和清单摘要，再进入共用的 HTTP/AList
下载队列。文件包和 ZIP 共用校验、暂存及不可覆盖的安装逻辑。下载页可以查看
进度、暂停、继续和重试。下载或失败期间，旧版本仍然保留并被选用。完成后自动把已启用旧版切换为校验成功的新版，并保留兼容选项。已关闭的插件和下载期间改动过的选择保持原样。其他客户端保留各自版本，运行中的客户端不能更改插件选择。

同一时间只检查一项操作，同一来源目录只请求一次；已安装版本数量没有固定上限。
切换客户端后丢弃前一个客户端的检查结果；离开页面不会终止后端下载。检查更新由用户
明确发起；`clientPolicy` 的 `latest` 规则还会在启动前检查并处理必需更新。不进行原生代码热加载。

## 共享数据包与依赖

`kind = "assets"` 的包只携带数据，例如多个插件共用的预生成图片。它不会交给原生 Hook 加载器，
不会修改或替换客户端文件，也不能带选项、补丁、原生库、overlay、service 或 companion 表。它唯一的表
指明被共享的文件夹：

```toml
[plugin]
id = "bubblefighter.fantasy.item-previews"
kind = "assets"

[assets]
root = "data"        # 包内相对文件夹；不允许越级、绝对路径或链接
```

导入或安装数据包时，该文件夹必须存在且至少包含一个文件。数据包可以很大：与其他插件包一样以流方式复制、
计算哈希并安装。

任何插件包都可以在 `[plugin]` 中声明所需的包：

```toml
requires = ["bubblefighter.fantasy.item-previews", "other.package@>=1.2.0 <2.0.0"]
```

每一项是插件 ID，可选地后接 `@` 和以空格分隔的比较（`>=`、`<=`、`>`、`<`、`=`），比较对象是 SemVer 版本。
也接受曾用 ID（`aliases`）。ID 不得重复，也不能依赖自身。

- **无需选择即生效。** 只要有一个启用且适用于该客户端版本的包需要某个数据包，该数据包就处于生效状态。
  玩家无需启用它，它也不会出现在客户端的插件选择中。使用满足约束且支持该版本的最新已安装版本。
  所有依赖它的包共用同一份已安装副本。数据包可以依赖其他数据包。
- **其他类型。** 被依赖的包若不是数据包，则必须在该客户端中自行启用。
- **安装。** 从商店安装某个包时，会同时从同一商店排队安装它依赖的包：选择最新的兼容版本，先安装被依赖者。
  已安装且版本满足约束的依赖会直接复用。商店无法为该客户端提供某项依赖时，安装会中止，并在提示中指明该依赖。
  商店条目必须带内联的 `plugin_definition`（见[自建商店](self-hosted-store.zh.md)），这样才能在下载前得知依赖。
  启动游戏前会等待该客户端已启用的包所需数据的传输完成。
- **启动。** 在改动任何客户端文件之前，若出现下列情况，启动会以现有的定义错误失败：依赖未安装、只安装了不满足约束的版本、
  依赖不适用于该版本、其他类型的依赖未启用、依赖形成环、数据包丢失了数据文件夹。
- **卸载。** 只要还有已安装的包依赖某个数据包，就不能卸载它。卸载最后一个依赖者后，共享数据仍保留，
  与玩家未主动移除的其他插件包相同。

Overlay 页面通过[插件包文件主机](hook/overlay.zh.md#插件包文件)读取这些文件。

### 插件策略（schema 2）

`schema = 2` 的清单可以声明任意多条关于其他插件包的规则，格式与[客户端策略](client-policy.zh.md)规则相同。
schema 1 清单照常加载；schema 1 清单若声明 `[[plugin_policy]]` 会被拒绝；早于 0.1.71 的启动器会拒绝 schema 2，
而不是忽略其中的规则。

```toml
schema = 2

[[plugin_policy]]
plugin = "bubblefighter.fantasy.native-ui-bridge"
type = "require"          # require | recommend | conflict
version = ">=0.1.5"       # 可选的版本约束，写法同 requires
builds = ["kr-812"]       # 可选：精确客户端 ID；省略时适用于该包支持的全部客户端
languages = ["zh"]        # 可选：启动器语言；zh 匹配 zh-CN 和 zh-TW
default_selected = true   # 仅 recommend：卡片默认勾选
```

| 类型 | 效果 |
| --- | --- |
| `require` | 启动前另一个包必须已安装并启用（数据包只需安装）。 |
| `recommend` | 启用该包时以勾选卡片推荐，启动时每个客户端只推荐一次。不会阻止启动。 |
| `conflict` | 两个包不能同时启用。存在已启用的冲突时拒绝启动。 |

规则只在其客户端和启动器语言下生效。语言不会禁止插件：在其他语言下该规则只是不生效，插件仍可安装和启用。
旧的 `requires` 项按不限范围的 `require` 规则读取；从商店安装时仍会一并安装每条 `require` 规则所需的包。

启用插件和启动游戏前都会先检查规则。有未满足的规则时，启动器为每条规则显示一张卡片：从已启用的商店**安装**
缺少的包、**启用**已安装的包，或**关闭**冲突的包。每张阻止启动的卡片还带有声明该规则的插件的开关；只有所有依赖都满足，
或关闭了该插件，才能继续启动。

### 安装与升级

- **安装。** 商店安装和本地导入的“安装后启用”默认开启。首次安装后会在所有支持该包的客户端上启用。
  如果启用会关闭另一个已启用的包，则跳过该客户端，不做任何改动。
- **升级。** 新版本会替换所有选择了旧版本的客户端中的选择，并保留各客户端的启用状态和兼容的选项。
- **旧版本。** 开启“删除旧版插件”（默认开启）时，不再被任何客户端选择的旧版本会被删除。本地导入和商店版本都适用；
  关闭该设置则不删除任何版本。
- **新支持的客户端。** 升级后的版本支持了此前任何版本都不支持的客户端时，启动器会为这些客户端分别显示卡片，询问是否在其上启用。
  在回答之前，重启后仍会询问；每个客户端只询问一次。

## 限制与存储

插件包、ZIP 输入和插件库不再设定固定文件数、条目数、版本数或字节上限。相对路径最长 240 个字符，必须适用于 Windows；路径越界、链接、重解析点、
设备名、大小写别名、文件与目录冲突、启动器元数据路径均会被拒绝。导入失败不会
影响已有客户端或插件版本。

默认插件库位于 `%LOCALAPPDATA%\FantasyTale\Launcher\plugins`。安装包存放在
`packages/<标识哈希>/`，单个待确认导入存放在 `staging/<令牌>/`。这些目录名只是
本地存储细节，不是插件标识。指定 `--data-root` 时插件库随数据根目录调整。启动器
使用期间不要手动编辑暂存或已安装的插件文件。目前尚无卸载界面，因为其他客户端
可能仍在引用保留的旧版本。

## 客户端版本推荐插件

服务器可通过公开 catalog 和登录／刷新响应增加按版本生效的推荐，接口见
[启动器账号会话](launcher-auth.zh.md)。当前目标服务器的必选项合并到本地版本推荐，
保持勾选并锁定，修改弹窗请求也无法遗漏必选项。已安装但禁用的包可直接启用；
缺失包使用已配置商店和现有校验下载队列。找不到的标识会明确阻止启动，不从认证
响应中获取任意代码。

必选状态在申请票据前、会话刷新后，以及持有客户端租约、创建模块启动计划前重新
检查；必选 Hook 初始化失败将终止该次启动。服务器策略不向客户端持久化全局
`Required` 标志，也不影响其他服务器。不支持 Hook 的游戏无法绕过检查。
推荐下载的绑定选择意图可跨重启恢复，用户之后修改选择仍可阻止自动启用。

服务器启用意图保存在独立 `.server-recommendation` 文件中。原 schema-one 任务
JSON 和 `.recommendation` 文件结构保持不变，旧版仍能读取任务。旧启动器忽略
新文件，对本地版本声明之外的远程推荐不能自动启用。

提示记录按声明的插件标识分别保存，后续新增推荐不会重复弹出旧的推荐。
服务器禁用 Hook 插件时隐藏可选推荐；强制文件组件仍可显示。延迟启用的选择校验记录单独保存，不向
第一版下载历史格式增加字段，让旧版启动器仍能读取原有任务记录。

客户端版本可以在自己的 `[plugins]` 表中声明可选的 `recommended` 插件列表。只有该列表非空时才显示推荐弹窗；启动器不会使用游戏级别或代码中的固定列表。已安装启用的可选插件从列表中隐藏；必选推荐即使默认已启用也会勾选并锁定；已经安装但未启用的插件只提供启用选项，不会重复下载。

新客户端在客户端文件准备完成后显示弹窗。已有客户端在第一次启动且发现推荐插件缺失或未启用时显示。确认记录保存在该客户端旁边，所以取消后不会在每次启动时重复弹出。确认的商店下载会把启用意图写入可恢复的下载记录，只有清单和文件字节校验成功后才启用插件。如果用户在下载期间改变了客户端的插件选择，启动器会取消这次自动启用，不覆盖用户的新选择。版本没有声明推荐项时不会生成记录，也不会显示弹窗。

启动器版本移除旧的内置商店管理版本后，如果客户端所选版本不再存在，会在客户端锁内迁移到更高的兼容内置版本，保留启用状态和兼容选项。已安装的历史版本仍可选用；其他插件标识不能触发此迁移。

插件更新通过校验后默认切换到新版，保留各客户端的启用状态和兼容设置。设置新增默认开启的“更新后自动卸载旧版插件”。清理会等待客户端空闲，迁移兼容选择后移除不再使用的旧版；关闭设置则保留旧版。启动器内置文件和仍被不兼容客户端使用的版本会保留。

[客户端策略](client-policy.zh.md)


导入插件面向共享插件库，不需要先安装或选择客户端。导入窗口校验文件夹或 ZIP
中的插件包，显示名称、版本、文件数量及大小。首次导入不会启用插件；已有插件的
更高版本会为兼容的现有选择升级，并保留启用状态与设置。

已安装包中的清单或设置错误会逐个隔离，并提供“查看详情”，正常插件继续显示。
异常提示采用统一的 InfoBar。有可识别插件标识和版本的包显示“检查更新”，发现兼容
新版后改成“立即更新”。插件卡片提供带卡片的卸载确认，
确认后移除该插件的全部托管版本和客户端选择。运行中的客户端保留当前会话使用的文件直至退出；其他文件操作占用配置时，在
修改选择之前阻止卸载。卸载范围只限插件库，不会删除客户端文件。安装弹窗可
随时关闭，已开始的任务继续在下载队列中运行。下载显示实际进度、大小和速度，
准备阶段尚无进度数据时使用不定进度条。
被拒绝的清单不会转换为可执行定义。自动检查可根据有效的插件标识从所有已启用来源
查找兼容新版。校验成功的升级保留
兼容设置和已启用选择，已关闭的选择保持关闭。当没有客户端再引用异常旧版且
已配置商店提供的新版已通过校验时，旧包原始文件移入插件库的 `rejected` 目录供诊断。

每次执行 `publish_plugins.py` 都会同时生成可直接导入的 ZIP，路径为
`FantasyTale/plugins/<game>/<plugin>-<version>.zip`，根目录包含
`plugin.toml`。商店条目的可选 `plugin_archive` 表记录 `source_path`、`size` 和
`sha256`。下载队列优先使用 ZIP，校验压缩包后，再按原始不可变发布清单逐项校验解压文件。
ZIP 不存在（HTTP 404 或 410）时回退到逐文件下载；权限、网络及完整性错误会明确报错。
暂停或重启后继续使用原清单及已校验的暂存内容。

发布一个干净的插件包目录：

```sh
python tools/publish-store/publish_plugins.py --package ./plugin-package --output ./publication --base-url https://files.example.org/
```

在发布进程中设置 `FT_ALIST_USERNAME` 和 `FT_ALIST_PASSWORD`。ZIP 和不可变对象全部通过
匿名校验后才提交商店目录。修改插件内容必须增加版本号，不要发布开发目录、会话文件或私有恢复档案。

补齐既有插件时，运行 `backfill_plugin_archives.py --base-url ... --output ...`，工具会根据
线上各版本已发布并校验哈希的对象生成 ZIP。添加 `--publish` 后上传、匿名校验，再为商店条目
添加 `plugin_archive`。它覆盖所有已发布插件版本，保留原清单和其他商店数据；发布期间目录发生
变化会停止提交，避免覆盖其他人的发布。

发布者仍可通过 `publish_plugins.py --archive` 流式创建可复现的单 ZIP 包，避免为每个
虚拟资源单独发送请求。发行清单校验完整 ZIP，插件库保留解压后每个文件的快照。
旧独立模型插件必须等统一替代插件发布后才能下架；先验证匿名下载和实际安装，再执行
下架，其他商店条目保持不变。

## 更新后的必选组件

插件升级保留原来的启用状态及仍支持的选项。当前配置要求必选的组件保持启用；
已经安装兼容包时，启动器会自动将它加入该客户端，不重复下载。
如果旧选择版本已经不存在，但有符合配置版本限制的较新兼容版本已安装，
启动器会在提示组件缺失前修复选择。仍存在的手动固定版本保持原选择。
启动检查前先处理已完成的待生效更新；由策略推导的必选标志变化不会取消更新，
用户修改版本、选项或启用状态时仍会阻止过时请求覆盖选择。
确实缺少下载内容时，仍通过安装进度与错误处理流程完成安装。

插件更名后，即使新旧包都不支持当前客户端，列表也只展示当前 ID。只有某个客户端
仍能使用旧包且没有符合条件的已安装替代包时，才展示旧 ID。其他客户端或运行中游戏
仍然需要的安装文件会继续保留。

自动恢复会检查所有引用同一失效版本的已添加客户端，先分别尝试迁移到兼容的
已安装替代包，再清理仍无法恢复的引用。同一失效版本只提示一次，同时从所有已保存
方案的各版本配置中移除该 ID 与版本，包括当前未打开的方案。其他版本及尚未安装的
导入条目保持原样。关闭弹窗也会清除对应的待显示通知。
