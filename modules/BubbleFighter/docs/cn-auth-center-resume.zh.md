# 国服认证与原生 Center 登录

[English](cn-auth-center-resume.md)

客户端特定的修复统一放在国服认证组件的 `login_bridge.dll` 中。共享 Messenger
宿主继续独立验证启动凭据并限制票据回调次数；没有向宿主加入国服偏移或修复逻辑。
组件只为严格核对的原生连接接续，暂存一份有界、已授权的认证回调数据。

## 一套逻辑，按版本配置

`native-passports.toml` 保存每个客户端的 PE 时间戳、允许的映像大小、连接对象位置、
票据字段偏移、原生字符串函数和精确指令签名，注释注明对应版本。初始化和调用前都会
验证函数签名与可执行内存。已知票据配置如果不符合签名，会拒绝认证；其他版本继续普通
认证流程。

组件只包装两种已知的登录接口。生命周期与设置调用仍使用宿主原对象。仅在当前映像
匹配票据适配配置时才需要包装登录接口。没有票据适配配置的映像
直接返回宿主原登录对象，即使开启了标题覆盖也不包装认证回调。宿主验证成功并
同步回调后，组件先通过客户端自己的字符串函数把已授权票据写入当前连接的原生票据
字段，再向游戏转发原回调。组件不获取第二张票据、不构造登录封包，失败回调不写入
票据，重复回调不重复交付。临时票据缓冲区在所有退出路径都会清零。

CN2012 的自动跳转通过 cn-324 sub_705710/sub_6FEEE0 创建空凭据的新连接，再由
cn-324 sub_705980 提升为当前连接。新 LoginStage 会在 cn-324 sub_584580 再次请求
认证接口。组件仅在已选服、连接已建立、待提升连接已清空、当前连接不同于首次写入的
连接、尚未完成登录且新凭据缓存为空时，向这次原生请求交付一次已授权回调。
cn-324 sub_584890 不可能已用空凭据发送登录，因此不会通过此路径重复发送。
尝试次数在调用游戏前消耗；转换和登录发送仍由原生 cn-324 sub_5852D0 完成。
不增加可执行指令或虚表补丁，缓存于初始化和结束时清零。每次启动只允许一次此类
接续，不是任意次数重放票据。

CN2011 使用相同的接续逻辑和较早的认证接口身份。cn-279 sub_6FBE60 通过
cn-279 sub_6FA250 创建空票据的新连接，cn-279 sub_6F1A70 将其提升为当前连接。
cn-279 sub_857F20 重置认证请求标志，cn-279 sub_8588F0 再次请求回调；选服后的
cn-279 sub_8580A0 通过 cn-279 sub_4203B0 发送原生登录。初次未选服时的回调只缓存
账号数据，不发送登录，该分支不依据连接票据判断；填入票据不会修改选服标志或提前
发送登录。原始和展开映像尺寸分别登记，原生函数仍严格核对运行时指令。不增加新 Hook。

CN2013 cn-406 与 CN2015 cn-717 在跳转时会复制票据，但新的 LoginStage 仍可能在
Entry 跳过原生发送后再次请求认证接口。这里沿用相同连接检查；非空票据还必须与
已授权票据完全一致。组件通过指纹匹配的原生函数核对地区、自动登录功能与提前退出
条件。Entry 跳过发送时，只交付一次缓存回调；Entry 已选择原生发送路径时，只消耗
冗余请求，不再回调、不再写票据、不再次请求宿主授权。这只确认原生发送路径已被
选择，不代表服务端已收包或认证成功。无法核对条件时仍由宿主拒绝重复请求。
cn-406 sub_576DD0 与 cn-717 sub_6DA700 在 Entry 完成后才处理此请求，不使用
认证接口返回值，并在调用后标记请求已处理。

CN2019 也复用同一接续：cn-774 sub_BA61D0 复制票据，cn-774 sub_BA6D70 提升连接。
目标的补丁响应请求新建 LogoStage，随后再进入 LoginStage。cn-774 sub_9FA4A0
只有在功能 1502 存在时才选择缓存票据发送路径；cn-774 sub_9FA7F0 在功能 1004
存在时再次请求认证回调。其 Entry 没有地区或提前退出分支，配置明确选择仅功能判断，
并指定 cn-774 sub_10695D0 通过 ECX 接收参数的调用约定。已授权票据精确匹配、
已连接、已选服、待提升连接为空及登录未完成等限制保持相同。Entry 未发送时，
cn-774 sub_9FB1A0 只接收一次已授权回调，由游戏自行构造登录。
这一步不增加可执行指令、虚表或协议修改。

CN2012 通过 cn-324 sub_401C00 创建原生 COW 临时字符串，用 cn-324 sub_401B10
赋值，并用 cn-324 sub_480390 释放临时引用。连接对象持有自己的有效引用。后续版本
调用各自的 24 字节原生字符串赋值函数。写入目标是票据字段，不是连接对象起始地址。

CN2019 的 cn-774 sub_44E030 接收字符地址和字符数，与较早版本接收原生字符串对象的
范围赋值接口不同，使用独立的 `span` 策略选择正确调用约定，并在调用前核对精确的
映像与指令签名。
CN2019 原始启动程序的映像大小为 `0x1B7E000`，展开映像为 `0x1B80000`，两者时间戳
相同，仍需通过精确的运行时赋值函数签名。只识别展开后的大小会在原生选服界面完成
启动之前拒绝原始程序。

旧的 CN2012 选服续接 Hook 已移除。这部分通过原生函数修改客户端状态，不修改游戏
指令；它仍属于进程内适配，不能称为纯协议或零侵入。选服、转换和登录封包均由游戏
原生流程完成。

## CN2011 可选名称覆盖

CN2011 cn-279 sub_405360 只从 CenterStatus 读取三个 u32，不能在协议中追加名称。
原生本地标题格式化函数保持不变；组件改用客户端自己的 COW 字符串函数更新已创建按钮的名称。

Launcher 通过 `bubblefighter.cn-center-names.v2` 能力提供完整服务器名称，TOML 包含
`schema = 1` 和带正整数 `id`、可选 `name` 的 `[[centers]]`。旧组件忽略此能力，
避免新显示数据激活旧格式化调用替换。名称缺失或为空时保留原文。组件只读取启动 session
中的显示元数据，凭据授权仍由宿主完成。

cn-279 sub_4A78A0 将创建完毕的选服对话框保存到 UiSystem+8，再经 cn-279 sub_4A9100
处理消息。Windows 窗口定时器在相同 UI 线程执行。核对对话框的两个虚表后，才读取
+356..+360 的按钮列表。cn-279 sub_64C8C0 按原生 Center 列表顺序创建按钮，因此可用
对应 Center 的 +2328 身份值查找名称，不按服务器地址匹配。所有列表范围和两个按钮
虚表都通过核对后才更新名称。快照按实际行数分配，在既有传输预算内保持有界，没有新增
64 项产品限制。

cn-279 sub_886A70 初始化按钮名称 +336；cn-279 sub_8868F0 每次绘制直接读取该字段。
组件用 cn-279 sub_401570 创建临时字符串，经 cn-279 sub_4012D0 赋值，再以
cn-279 sub_401510 释放临时引用。按钮保留有效的原生引用，最终仍由原生析构释放。
选中服务器、容量、连接、原始虚表和可执行指令均不修改。

cn-279 sub_8868F0 用参数 5 在固定 70 像素区域内居中绘制名称；cn-279 sub_540FF0
减去文字宽度的一半，长名称便会在按钮左边被裁切。提供了名称的按钮改用独立虚表副本：
保留原完整对象定位信息和 48 个入口，仅适配第 3 个绘制入口。没有提供名称的按钮仍使用
原始虚表及原始对齐方式。

绘制适配器复制 cn-279 sub_8868F0 使用的 340 字节只读视图，不改动实际按钮；以空名称
视图调用原绘制函数，继续使用原背景和字体，再以原坐标调用 cn-279 sub_5375B0，使用
参数 4 保留垂直居中并改为左对齐。绘制期间持有名称的 COW 引用，异常结束也释放引用；
线程局部标志阻止重入时更新名称。副本和原调用地址保留到进程退出，组件结束后残留的
适配按钮直接调用原绘制函数。重新初始化时拒绝改变已固定的绘制参数。不修改原始代码
或原始虚表。这属于仅作用于按钮绘制的 Hook，不能称为零 Hook 功能。

初始化和原生字符串调用前核对映像指纹及精确函数签名。无效可选元数据保留原生名称，
不放宽必须通过的票据校验。结束时取消窗口定时器；回调模块保留到进程退出，保证已入队
回调不会指向已卸载模块。不创建工作线程，不新增消息 Hook。

cn-279 sub_8868F0 将名称直接作为格式字符串传给 cn-279 sub_5375B0，后者调用原生
宽字符 printf 格式化函数，调用方没有提供额外名称参数。因此存储时将百分号写成两个
百分号，绘制后仍按字面显示原名；存储范围覆盖 128 个百分号的最大输入。

## 验证

使用 Visual Studio v145，Release|Win32：

```powershell
msbuild native/tests/cn_auth_tests.vcxproj /p:Configuration=Release /p:Platform=Win32
artifacts/tests/cn_auth_tests.exe
python tools/package-cn-auth.py --gpk <verified-gpk-payload> --output artifacts/cn-auth/cn-auth-1.0.14.zip
```

实际 DLL 的 989 项检查全部通过，覆盖认证 ABI、凭据接续、原生 COW 生命周期、真实
Windows 定时器、65 项列表、共享空字符串、无效或缺失元数据、忽略 v1 元数据、实际
printf 格式化以及 128 个百分号边界。绘制检查覆盖虚表定位信息和全部 48 个入口、实际
按钮不变、定时器及绘制重入、异常清理、两种原生边距、结束后的原绘制路径、重新初始化
和无效视图或虚表形状。原始代码、原始虚表、选服和连接状态保持不变。另以只读方式
对原始启动程序核对函数和虚表身份。

采用相同 UI 字符串更新路径的较早候选，已在本机隔离的原版 CN2011 显示六个中文名称，
原格式化 CALL 指令保持不变。
观察在 70.39 秒时因本地测试环境的 55 秒选服期限结束而正常退出，退出码为 0。这验证
候选显示路径，不代表精确冻结包的客户端验收或生产服登录，也不能称为连续观察
100 秒；原生登录验收单独记录。

最终 1.0.14 DLL 在隔离原版 CN2011 中运行 100.05 秒，六项完整名称均存在，原始代码
保持不变，副本的 RTTI 相同，每个提供了名称的按钮都只有第 3 个入口被适配。用户已确认
左对齐外观正常。本地显示测试不代表生产服务器登录验收。

## CN2014 启动修复

组件 1.0.16 需要 Launcher 0.1.54 和 FtHook 3.7.1。唯一的 cn-706 专属补丁
将 cn-706 sub_868920 内 0x868BA3 的调用改为跳转到 cn-706 0x868C16。
原始启动流程依次调用 sub_865110（已停用的更新器）、sub_865440（初始化）
和 sub_865670（启动）；更新器在游戏认证之前失败并显示 Update Error。
接回位置的栈深度保持一致，原生退出流程 sub_AEE4BC 和 sub_AEE6EA 会检查
模块和入口是否存在。写入前必须匹配唯一的周围签名及准确的原始调用字节。
不包含身份上报兼容补丁。其他版本没有生效补丁，沿用既有文件部署和认证行为。

离线校验已匹配原始解包映像。压缩的 cn-706 客户端仅将此组件放入原生会话，
成功连接本机 TCP 监听器并持续运行 150 秒，没有 Update Error 或插件加载报错，
维护者确认两种弹窗均未出现。此测试端不提供游戏回复，不能据此确认线上登录、
选服、切服或开局正常。
